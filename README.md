# Bahn Control Room — dispatch risk

A control room for Bahn's car deliveries that shows a person **only the orders that need them**, with one decision each, and a dispatch-risk agent that does the legwork first.

Prototype scope: Bahn's main markets. Every gig that starts or ends in Germany or Denmark (45 orders), plus gigs that start and end in Finland or Estonia (36 from the Bahn snapshot and 5 fictional Finland–Estonia demo orders in `data/demo-ee`, generated by `node scripts/estonia-demo.mjs`). The scope is `SCOPE` and `MAIN` in `lib/data.mjs`. The Estonia orders cross the Gulf of Finland on the real published Helsinki–Tallinn timetable. UI in English and Finnish, including the agent's proposals.

## Run it

You need Node.js 22.13 or newer (24 recommended). No database server and no Docker: the database is one SQLite file that ships with the repo (Node has SQLite built in). The only dependency is the official Anthropic SDK.

```sh
git clone https://github.com/tommy2006/bahndesk
cd bahndesk
npm install
cp .env.example .env      # optional: add ANTHROPIC_API_KEY to run the agent live
npm start
```

Open http://localhost:3000.

Without a key everything works, including the agent proposals already saved in `data/runs.json`; only new agent runs and chat need a key. The agent uses Claude (`claude-opus-5-5`) when `ANTHROPIC_API_KEY` is set, and Groq when only `GROQ_API_KEY` is set.

## What Bahn told us, and how the engine follows it

From Bahn's answers at the event (25 Oct 2026):
- **Worst failure:** a car that could be delivered but isn't. A driver who picked up a car and has been silent for 12 h or more (no app position, no message) is the highest-weighted signal and always tops the queue. At 6 h the agent asks the driver first. A GPS gap alone weighs little, because GPS often drops out in the German countryside.
- **The latest arrival is soft.** A first late car is handled by the agent; repeated lateness for the same customer escalates.
- **Every driver is trained for every car,** and cars over €100k are rare. Car value does not change the threshold or the driver choice.
- **Travemünde** is a known trouble spot, and **winter tyres** are checked once winter starts. There is no Bahn data on EV range in winter, so range figures are labelled as estimates.

The demo set includes one fictional order, CD-421106, showing the silent-driver case.

## How it decides what needs a person

Every order is scored on every request by a deterministic engine (`lib/engine.mjs`):

1. Each signal becomes a **reason** with a risk `r` (0–1), a factor (readiness, schedule, route, car, driver, driver market, news) and **the record it came from**.
2. **Confidence** that the order delivers on time without a person = Π(1 − r). Any reason can be clicked to open its source record.
3. Reasons the agent can deal with alone (ask the driver for a position, send a weather briefing, plan charging) don't count toward escalation.
4. An order goes to **Needs you** if a human reason blocks it, or its human-only confidence falls below 55 %, the same for every car.
5. Shared causes are grouped. One port strike affecting five ferries becomes **one** decision, not five alerts.

It's cheap and explainable, so it can run on a million orders. The language model only works on the orders the engine flags.

## The agent

`lib/agent.mjs` is a tool-calling loop on Claude (`claude-opus-5-5`), with Groq as a fallback. It reads first (order, messages, driver record, live conditions, booked ferries and real Helsinki–Tallinn sailings, alternative drivers). It may ask the driver or pickup site, which is simulated. Then it must either `propose_decision` (a person approves) or `resolve_without_person`. That second option is refused if anything needs a human. It never contacts customers and never changes a booking, date, cost or driver without approval. At startup it works through the flagged orders in the background, so the proposal is waiting when a person opens the order. Answers to a person are at most four short bullet points.

## Evidence a dispatcher can read

Every reason links to the record behind it. The drawer (`lib/explain.mjs`) explains that record in plain words: what it is, what it says, and when (in Helsinki time). Messages are quoted as written. IDs, codes and raw field names are hidden under "Show technical details".

## The database: `data/bahn.db`

Everything the app knows sits in one SQLite file. Open it in any SQLite viewer, such as DB Browser for SQLite:

| Tables | What |
|---|---|
| `orders`, `drivers`, `vehicles`, … (47 tables) | The Bahn snapshot, one table per dataset file |
| `ref_routes` | Road route for every Finnish leg: distance, drive time, geometry (OSRM over OpenStreetMap) |
| `ref_pois` | Every fuel station, EV charger (with socket types) and rest area in Finland, about 6,500 places (OpenStreetMap) |
| `ref_route_pois` | Which of those lie within 2 km of each route, and at which km |
| `ref_ferry_sailings`, `ferry_terminals`, `travel_reservations` | Real Helsinki–Tallinn sailings, terminals, and the bookings in the snapshot |
| `ref_news` | Strike and disruption notices |
| `live_weather`, `live_traffic` | Every live fetch, appended, so there is a history |

Reference data is fetched once and saved. To add routes for new cities or refresh the map data:

```sh
npm run build-db              # fetch only what is missing
npm run build-db -- --refresh # re-download routes and stops
```

Map data © OpenStreetMap contributors, available under the ODbL.

No invented operators or travel quotes: the snapshot's made-up ferry lines, airlines, hotels and quoted options are dropped when the data loads (`lib/data.mjs`). Demo and live data are labelled in the UI. If live sources are unreachable the app uses the last saved fetch and says so.

## Score your own order file

The **Score a file** button (or `/#upload`) takes a CSV or JSON export of orders. Each order is scored with the same rules, thresholds and live data as the control room, and gets:
- a lane: *needs a person*, *agent can handle*, *on track*, or *check the data*;
- a score;
- the main reason, and every reason with its source: "Your file, row 7, last_driver_contact", "OSRM route (saved)", "Fintraffic, live", "Bahn's answers".

Uploaded orders are scored against the real clock. Nothing is stored, booked or sent, and results download as CSV.

- **Columns:** `ref`, `pickup_city`, `pickup_country`, `delivery_city`, `delivery_country`, `pickup_at`, `deliver_by` are required. Optional: `status`, `car`, `fuel`, `driver`, `driver_on_time_pct`, `driver_claims_12m`, `last_driver_contact`, `ferry_booked`, `pickup_confirmed`, `receiver_named`, `notes`. Common aliases (`from`, `to`, `deadline`, `reference`…) and semicolon CSVs are accepted. The full list with help text is in `lib/score-file.mjs` and on the page.
- **What it checks:**
  - drive time with EU rest breaks, against the deadline;
  - the real Helsinki–Tallinn timetable;
  - Germany → Finland via Travemünde, and the strike notice;
  - Bahn's silent-driver rule (6 h: agent asks; 12 h: person);
  - no driver close to pickup, and a missed pickup;
  - driver record;
  - dealer and receiver confirmations;
  - live weather and road notices on the route;
  - bridges and ferries;
  - winter tyres and EV range;
  - risky words in notes ("keys", "papers", "damage"…).
- **Data quality first:** missing fields, unknown cities, unreadable dates and duplicate references go to *check the data* instead of getting a made-up score.
- **Synthetic files** (fictional orders, real cities and timetables) are under `samples/`, and fresh copies with dates relative to today are at `/api/samples/<name>`:
  - `nordic-week.csv`: 12 Finland/Estonia orders;
  - `germany-denmark.csv`: 10;
  - `messy-export.csv`: semicolons, other column names, gaps, a duplicate and an unknown city;
  - `orders.json`;
  - `template.csv`.

  `npm run samples` rewrites them.
- **API:** `POST /api/score` with `{"filename": "orders.csv", "text": "<file contents>"}`.

## MCP server: the same tools for any AI assistant

`mcp/server.mjs` is a stdio MCP server with no extra dependencies. Bahn's own assistants or agents can call:
- `score_orders`: a CSV/JSON file goes in; lanes, scores and sourced reasons come out;
- `orders_needing_a_person`: the control room queue;
- `explain_order`: every reason for one order;
- `sample_order_file`: a synthetic file to try.

All tools are read-only.

```sh
claude mcp add bahn -- node /path/to/bahndesk/mcp/server.mjs
```

Claude Desktop (`claude_desktop_config.json`):

```json
{ "mcpServers": { "bahn": { "command": "node", "args": ["/path/to/bahndesk/mcp/server.mjs"] } } }
```

## Two clocks: the orders and the weather

The top bar shows both: **Orders as of Sun 25 Oct, 12:00 · Weather & roads live, updated 11:46**.

- **Orders:** Bahn's snapshot was taken on Wed 21 Oct 2026 at 12:00 (Helsinki). Deadlines, countdowns and "silent for 13 h" are measured against that fixed moment. If it ran in real time, every order would be days overdue.
- **Demo day:** `lib/clock.mjs` moves every date forward 4 calendar days when the data loads, so the snapshot reads as the demo day. Local wall-clock times stay the same; Finland and Germany leave summer time that night, so a plain +96 h would be off by an hour. Dates written in text move too ("Thu 22 Oct" → "Mon 26 Oct", "ke 21.10." → "su 25.10.").
- **Original files untouched:** the files in `data/bahn` are not changed. `SHIFT_DAYS = 0` shows the original snapshot.
- **Saved outputs:** the saved agent proposals (`data/runs.json`) and Finnish cache were moved once to match. Rows keep their wall-clock times.
- **Weather and roads** are fetched live.
- **In production,** Bahn's live order feed replaces the snapshot and the order clock becomes "now".

## Weekly report: caught vs missed

The **Weekly report** button (or `/#report`) is for management. `lib/report.mjs` takes every problem the data records on an order (an incident, a car not found, a refused check-in, a cancellation, a late delivery, or a high/critical alert from Bahn's own system). It then asks:

- **Warned in advance?** It re-runs the risk rules using only records dated *before* the problem, plus what was known at planning (route, crossings, driver track record). Live weather, traffic and countdowns are left out because they describe today. If those signals alone would have sent the order to a person or the agent, it was warned in advance, and the report shows how many hours ahead.
- **Flagged when it happened?** Otherwise: was the order in front of a person or the agent once the problem was on record?
- **Missed:** neither. Each miss comes with what would catch it next time.

For week 43 (data up to Sun 25 Oct 12:00), 13 of 87 orders had a problem (15 %). 10 were caught: 2 in advance (median 27 h ahead) and 8 when they happened. 3 were missed: a late delivery and two cancellations. The report also shows today's load: how many orders need a person and how many the agent handles. It says plainly that orders raised without a recorded problem are open risks, not proven false alarms.

## Deploy to Vercel

The same code runs as one Vercel function (`api/index.mjs` → `server.mjs`'s `handler`); `vercel.json` serves `public/` and rewrites `/api/*` to it.

1. In Vercel: **Add New → Project**, import `tommy2006/bahndesk`. Framework preset: **Other**. Leave build and install commands as default.
2. **Settings → Environment Variables:** add `ANTHROPIC_API_KEY` (optional; without it the saved proposals still show, but new runs and chat are off).
3. **Settings → General → Node.js Version:** 22.x or newer (`node:sqlite` is needed).
4. **Deploy**, then open `https://<project>.vercel.app/api/overview` to check it returns JSON.

On Vercel, decisions, new agent runs and new translations are written to the function's `/tmp`. They last while that instance is warm and reset on a new deploy or cold start. Live data refreshes on the first request after 10 minutes instead of on a timer; that request waits about 3 s for it. Agent runs can take up to the 60 s function limit.

## Running the agent ahead of time

`AUTO_AGENT=1` in `.env` makes the server work through flagged orders at startup. Alternatively, stop the server and run one pass. It also adds Finnish translations to proposals that lack them:

```sh
node --no-warnings scripts/agent-pass.mjs
```

When the main model (`GROQ_MODEL`, default `openai/gpt-oss-120b`) hits Groq's daily cap, the agent switches to `GROQ_FALLBACK_MODEL` (default `openai/gpt-oss-20b`), which has its own quota.

## Agent speed

On Groq's free tier the model allows 8,000 tokens per minute. One order takes 4–7 model calls with a growing context, roughly 10–15k tokens, so each order takes about a minute and most of that is waiting for the rate limit. The agent waits and retries automatically. A paid Groq tier, or any provider with a higher limit, makes the same code run in seconds per order.
